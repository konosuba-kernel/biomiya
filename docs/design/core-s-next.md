# Core S 下一版语言与编译器改进方案

日期：2026-10-12。设计代号 **S-next**，用于区分当前 B3.1 与本方案，不是已发布的语言版本。

本方案围绕“自举、简单、现代”的优先级，重新确定语言规则、编译阶段、数据表示和引导链。允许破坏源码、ABI、清单和工具接口兼容性。旧编译器保留为引导工具，新实现不需要接受旧程序。

**状态：P0–P5 及最终整合已独立验收通过；10,991 行仍超过 8,000 行原型软预算。** Q 的稳定 ID 和源码/映像拥有者边界已经补齐并独立通过。实际状态与候选身份见 [执行 DAG](../../core-s/next/delivery.md)，当前语言接受集见 [S-next 0.1 参考](../../core-s/docs/reference/s-next-0.1.md)。本文独立于 [R1a 草案](reference-next.md)，不继承其中未列入的语言承诺。

## 1 目标与取舍原则

第一目标是从可追溯的种子建立新编译器的自编译固定点，并最终能够把编译器运行支持迁往 SOS。第二目标是让读者能解释一次编译的状态、数据和失败路径。现代能力围绕具体系统实验加入，不以通用语言的功能覆盖为目标。

复杂度账本覆盖编译器、运行库、平台代码、必要具体容器与示例。测试、文档、生成物、构建工具、冻结的引导源码和外部基础设施分别列账。把逻辑移入库、生成器或汇编，不算消除成本。

本轮不引入用户泛型、宏、闭包、借用检查器、通用编译期执行、完整 HIR、SSA、优化 pass 框架、通用插件 ABI、多目标后端或完整 C 互操作。固定 RV64，保留直接 ELF 输出、具体容量限制和逐函数存储复用。

## 2 当前实现与问题依据

比较对象为工作区中的 B3.1 维护重构实现，13 个生产 VT 模块共 7,988 物理行、240,327 字节。其目标 ELF SHA-256 为 `90c9523de43bebbd0a6932e74abc8cd670b60478c3b4f0fc1eff74fbf4cfb686`。该源码在编写本文时尚有未提交改动，不能用当前 HEAD 代替它的完整身份。执行阶段首先冻结源码及依赖哈希；既有结果见[重构记录](../../core-s/docs/refactoring.md)。

| 发现 | 当前实现 | 结构上的代价 |
| --- | --- | --- |
| 赋值先检查左侧取得类型，运行时却要求右侧先执行 | `check.statement` 捕获左侧 IR，检查右侧后重放 | 一条赋值需要临时撤回与重放生成状态 |
| defer 接受代码块 | `check.cleanup`、`ir.begin_capture/end_capture/instantiate` | 任意清理片段、标签映射及出口展开 |
| 类型准备重新读取声明源码 | `types.prepare` 保存 token 和诊断位置，seek 后恢复 | 布局和名字解析依赖扫描器时序 |
| 常量存在两个结构入口 | `types.constant_inner` 读 token；`parse.constant_inner` 读 AST | 算术规则虽已共享，表达式解释和类型上下文仍需同步 |
| 类型、AST、指令通过整数标签及复用字段表示 | `model.Type/Decl/Inst`、`parse.Node` | 字段含义依赖注释，错误组合可被构造 |
| 状态分布在多个模块 | 生产模块有 130 个 `static mut` 声明，包含表、游标、计数器 | 初始化、写入和失效的责任难以局部辨认 |
| Rust 与 VT 并存 | `core-s/src` 与 `core-s/bootstrap` | 持续双实现演进会重复承担语义维护成本 |

去除字符串和注释后，当前 13 个生产 VT 模块及 VT 运行库没有实际的块式 defer 语句；`runtime/linux.vt` 有两处 `?`。`ir.begin_capture` 在生产检查器中的调用点为赋值和 defer 两类处理。以上只说明迁移自身的成本较低，不能据此否定资源清理对系统程序的价值。

## 3 语言边界

### 3.1 保留的基础能力

保留 unit、bool、u8、u32、usize、具体结构、数组、切片、原始指针、模块、普通直接调用、标量和指针 C extern、语句式分支与循环。保留明确的 checked/wrapping 算术、索引检查、普通值复制及显式 unsafe 合同。

局部变量必须初始化。指针和切片复制不复制目标对象，不证明有效期、唯一访问或资源所有权。首版不增加一般的流敏感初始化证明，也不通过取消 unsafe 标记暗示这些保证已经存在。

新的硬件整数宽度、有符号数与间接调用在系统切片中单独验收；不能在实现过程中因为写起来方便而自动加入。裸存储、对齐、取址和内存访问仍须遵守明确的目标合同。

### 3.2 统一求值顺序

普通操作数和调用实参从左到右求值；每个实参在求值完成时保存其值，后续实参的副作用不能改变已保存实参。短路运算保留条件求值。

赋值按以下顺序执行：

1. 求出左侧目标地址，执行必要的索引与地址检查。
2. 求出右侧值；在需要时保存聚合快照。
3. 写入第一步确定的目标。

因此 `a[index()] = value()` 先调用 `index`，再调用 `value`。右侧即使修改用于寻址的变量，也不会重新计算目标。目标地址在右侧执行期间失效属于程序违反存储合同，赋值规则不提供借用证明。

预期删除赋值中的 IR 捕获与重放。普通参数快照、聚合复制、短路分支和运行时检查继续存在。

### 3.3 将 defer 限定为保存调用

拟议形式为 `defer close(fd);`，不接受代码块、间接调用或产生非 unit 结果的清理函数。

注册时解析直接被调用函数，从左到右求值并复制实参；全部求值成功后才登记调用。保存的是实参值，指针仍只保存地址。执行清理时不重新读取原实参变量，不重新解析名字。

每个作用域维护自己的清理列表，正常退出时逆序调用。return 先保存结果再清理；break 和 continue 清理离开的作用域；循环体每次迭代结束执行本次登记的清理。panic 直接终止，不展开；清理函数自身 panic 时，后续清理也不执行。

实现记录为具体的 `CleanupCall { callee, saved_args, scope, span }`。各出口生成普通 CALL，不复制任意 CFG，也不需要捕获片段的标签重映射。循环内的注册随本次块退出销毁，不形成跨迭代无限增长的运行时注册栈。

需要报告 close 失败的路径应显式调用并检查结果；unit 清理函数必须明确其忽略、报告或终止策略。defer 不提供自动资源管理和失败回滚证明。

### 3.4 用具体标签类型统一数据建模

增加具体变体类型，删除特殊的 `Result<T,E>` 类型构造及 `?` 表达式。错误通过具体结果类型和显式 match 传播。当前固定 Result 本身不是用户泛型引擎；此次交换的目的在于统一数据表示与控制流机制。

拟议语法示意，尚不是可编译样例：

```text
enum ReadResult {
    Read(usize),
    Failed(IoError),
}

enum Expr {
    Empty,
    Integer(Literal),
    Name(NameId),
    Binary(BinaryExpr),
}
```

每个变体无载荷或携带一个具体类型；多字段载荷使用具名结构。只允许顶层标签匹配及整个载荷绑定，无嵌套模式、守卫、类型推导搜索或隐式分配。闭合枚举要求所有标签显式覆盖，不提供通配分支掩盖后来增加的变体。整数分派另用有限常量分支与默认分支，不进行区间穷尽推理。

首版布局为 u32 标签和足够容纳最大载荷的区域：载荷起点向所有载荷的最大对齐取整，整体尺寸再向整体对齐取整。标签从声明顺序的零开始；无 niche 编码、隐式装箱和外部聚合 ABI。重复标签拒绝；按值递归依照普通布局规则拒绝，通过 ID 或指针连接的递归允许。

对具体变体的载荷只能在匹配分支内或构造时访问；原始字节输入不能通过普通 cast 自动成为合法变体。编译器不承诺检测 unsafe 伪造的非法表示。

先以 AST、IR、三个具体 I/O 结果类型测量成本。验收必须同时计入类型声明、匹配代码、存储初始化和编译器支持代码。若交换不划算，应修改方案并重新验收，不保留两套机制作为默认兼容路径。

### 3.5 分离常量、布局与初始化

布局前 const 只允许显式类型的整数或 bool、字面量、之前可见的常量、有限运算与转换；禁止函数调用、sizeof/alignof、取址、块和模式匹配。跨模块引用只能指向已完成的导入模块常量。数组长度只使用该类别常量，结果要求 usize。

具名类型先登记身份再计算布局，因此允许指针递归和函数相互调用。仍需检测类型的按值循环。布局完成后，函数体中的 sizeof/alignof 只是查询；结果不能回流到数组长度或具名布局定义中。

所有表达式使用同一语法解析入口；受限常量求值只遍历允许的节点并调用共享标量规则，不再单独维护一份基于 token 的优先级求值器。

静态初始化允许有限的标量、字符串、具体聚合、变体构造及静态根地址重定位，不执行用户代码。先检查为有类型的初始化记录，再输出数据和重定位；序列化器不重新解析名字、判断语法合法性或调用源码解析器。列表与重复的所有子项都检查，零重复长度不豁免错误。运行期 `[expr; 0]` 仍求值 expr 一次。

提供有期望类型的 `zero` 初始化值，避免定长表必须书写大段全零字段构造。零有效类型限于 unit、bool、整数、允许 null 的原始指针、空切片，以及递归零有效的结构和数组；变体仅当第一个变体无载荷时零有效。其他类型拒绝 zero。需要全零 arena 的 Expr 可以显式定义 Empty；读取模块必须拒绝把未分配槽当作已构造表达式。

复杂状态由普通 init 函数显式构造。语言不提供自动模块构造器；驱动或程序入口负责初始化顺序及失败清理。

### 3.6 让语法与名字绑定独立

每个文件明确所属模块，通过显式导入及模块别名访问外部名字，取消 `root::` 特殊路径。导入图必须无环；同一模块内部仍允许已收集签名之间的前向调用和相互递归。

结构构造采用明确标记，如 `make module::Point { x: 1, y: 2 }`。变体构造使用类型限定的标签，如 `Expr::Integer(value)`。解析时保留路径，绑定阶段判定函数或构造器，不依据当前符号表更换语法。

语法解析不执行 `resolve`、`layout` 或 `shadowed`。条件后的代码块和结构构造不再通过 `head` 参数区分。限定名中的模块别名与类型位置按固定名字空间规则处理，不在多个解释之间回退尝试。

公开类型允许私有字段；字段访问与构造按定义模块检查。NameId、TypeId、SlotId 等使用不同的单字段结构，不增加独立 newtype 语法。包装类型防止 ID 类别混用，不证明索引范围和 arena 有效期。

### 3.7 只做局部、单向定型

函数参数、结果、字段和 const 均显式定型。局部变量可从已确定类型的初始化器取得类型；无上下文的整数字面量必须写后缀，不选择默认整数类型。

检查接口分为 `synth(expr)` 与 `check(expr, expected)` 两种模式：前者从表达式本身获得具体类型，后者只向子项传递已知期望类型。无类型变量、统一、回头重试或兄弟节点反向传播。

算术有外部期望类型时，两侧按该类型检查；否则先定型左侧，再检查右侧。比较先定型左侧，再按其类型检查右侧，不使用比较结果的 bool 类型检查操作数。因此 `n == 0` 可接受；没有其他上下文的 `0 == n` 要求左侧后缀。常量与运行期表达式采用相同的标量定型规则，差别仅是常量允许的节点集合。

数组列表和 null 等缺少自身完整类型的构造继续要求上下文。首版只接受语句式分支，不求解多个分支之间的公共类型。

## 4 编译阶段与数据合同

```text
读取不可变源码
  → 解析模块与声明头，记录函数体区间
  → 绑定声明，计算布局前常量
  → 完成具名类型布局、函数签名
  → 检查并序列化静态初始化
  → 对每个函数：解析 AST → 检查并生成 typed IR → 验证 → 分析 → RV64 发射
  → 汇编适配、符号修补、ELF 构造
  → 所有要求通过后发布
```

| 阶段 | 输入与输出 | 必须保持的边界 |
| --- | --- | --- |
| 声明解析 | Source → HeaderSyntax、BodyRange | 检查文法，不需要布局；区间扫描通过 lexer 处理字符串和注释 |
| 名字绑定 | HeaderSyntax、导入表 → 已绑定声明 | 路径绑定为稳定身份，不重新读取声明文本 |
| 常量与布局 | 已绑定声明 → 常量值、具名布局、签名 | 不持有或修改扫描器；无布局到布局前常量的反向边 |
| 静态初始化 | 初始化语法、类型表 → InitData、Relocations | 完整验证后序列化，不把部分数据当作已完成对象 |
| 函数检查 | FunctionAst、声明表 → CheckedFunction | 唯一的语言执行语义入口；显式 Place 与 Value |
| 分析与发射 | CheckedFunction → 摘要、机器码 | 分析只读语义 IR，目标侧表独立 |
| 发布 | 已完成映像、分析结果 → 输出文件 | 类型、链接或要求的分析失败时不发布新 ELF |

函数体仍可根据 BodyRange 在轮到它时解析；这属于驱动控制的阶段入口，不是布局器递归 seek。只保留一个函数的 AST 和 IR，不要求全程序函数 AST。

具名类型准备完成后条目只读。函数检查时可以通过类型池拥有者追加具体指针、数组和切片类型；既有 TypeId 的含义、字段和布局不能改变。不能将“追加新类型”与“修改已完成类型”混为一谈。

IR 保留槽式、非 SSA 表示，控制流使用块或标签 ID。明确区分值、位置、复制、调用和终结操作；后端不处理 defer、问号、模式或源级字段查找。先保留一次线性的 IR 合法性检查，迁移时不以“仅内部使用”为由删除检查和错误测试。

后端读取已验证布局，管理自己的帧偏移、机器标签与回填。标量规则适合纯函数；有限 arena 构建保留原地修改，不引入通用 visitor、持久化集合或效果框架。

## 5 状态所有权与生命周期

| 拥有者 | 内容 | 写入和失效规则 |
| --- | --- | --- |
| SourceStore | 源码字节、文件身份、位置映射 | 输入完成后只读，持续到编译结束 |
| DeclarationStore / TypePool | 名字、绑定、签名、类型条目 | 具体构建入口写入；完成条目只读；新类型可追加 |
| ParseContext | 当前文件、token、位置、递归预算 | 一次解析私有；其他阶段不能访问游标 |
| FunctionWorkspace | AST、绑定、作用域、IR、CleanupCall | 驱动开启和结束一个函数；复用时全部临时 ID 失效 |
| AnalysisStore | 稳定 DeclId 与调用摘要 | 在函数 arena 释放前提取，不保存 AST 或 Slot 引用 |
| ImageBuilder | 代码、数据、符号、重定位和容量 | 发射阶段追加、链接阶段修补、完成后只读 |

不建立包含所有字段的巨型 CompilerContext，也不把每个函数都改成传入所有表。接口只接收实际依赖的小上下文、表描述符或指针；大型数组保持单一存储位置，不按值传递。

`begin_function → parse/check → finish_ir → analyze/emit → end_function` 由驱动控制。函数构建器失效后，不允许后端保留其句柄。用模块私有字段、构造入口、边界断言和跨函数复用测试落实合同；这不是语言层的借用或生命周期证明。

错误位置作为 Span 显式传入诊断接口。词法当前位置只属于解析；检查器不能通过改 token 选择错误位置。首版继续允许命令行编译失败即停止，不要求每个内部函数都返回 Result；纯规则返回小的值或失败记录，I/O 错误在具体边界显式处理。

现有静态预留空间不是实际峰值 RSS。调整内存时分别统计保留容量、实际最高计数、目标静态段、单函数 frame 和目标运行结果。阶段复用只能覆盖生命周期确实不重叠的区域，不能让仍活跃的源码、IR、数据或修补引用失效。

## 6 一次性引导与后续单实现维护

定义 B 为冻结的 B3.1 目标编译器，P 为“用 B3.1 编写、接受 S-next 的编译器源码”，Q 为迁入 S-next 的编译器源码。

```text
B(P)   = E0      新语言的第一个可执行编译器
E0(Q)  = E1      新语言源码产生的第一代
E1(Q)  = E2
E2(Q)  = E3      要求 E2 与 E3 完整 ELF 相等
```

P 可以继续使用 B3.1 的 Result、字段记录和旧语法，因为它由 B 编译；它接受的输入语言由 S-next 规则决定。P 不必能够编译自身。Q 则必须完全符合新语言，可使用具体变体及新存储接口。不能在 Q 尚未迁移时把 P 的测试通过称为新语言已自举。

冻结原有 Rust C0、其四个根目录共享源码依赖、Cargo 锁文件、平台运行支持、B3.1 源码与重建步骤。后续新特性只进入 Q；Rust 不再追赶新语义。P 作为一次性迁移来源保留，不再与 Q 长期同步开发。

验收从干净声明输入构建，使用绝对路径启动 qemu，目标进程 PATH 为空，guest 栈仍按 1 MiB 验证。记录每代输入哈希、编译器哈希、产物、资源统计及命令。检查目标没有调用宿主代编译服务，也没有读取自身 ELF 复制产物。

固定点只证明该编译链稳定。另需独立期望的语言正反例、机器码/ABI 检查和源码扰动实验；修改 Q 的可观测行为后，输出必须产生对应变化，不能只比较未扰动的两个相同文件。

## 7 平台能力与分析扩展

基础语言、机器能力、静态分析分别管理，不提供一个可任意改变语义的统一扩展接口。

| 类别 | 当前方案 | 加入下一项的条件 |
| --- | --- | --- |
| 基础语言 | 固定具体类型与结构化控制流 | 在自举、库及教学样本中证明净收益 |
| 机器能力 | 固定 RV64，标量/指针 FFI，现有有限汇编适配 | 一个真实样本要求的宽度、调用约定或特权操作 |
| 运行支持 | Linux 与 SOS 各自提供具体读写、退出等模块 | 相同编译器核心在两个平台完成端到端实验 |
| Blocking | 当前直接调用 may-block 摘要 | 保留 Verified、Violation、Unknown 的区别 |
| 后续资源/并发分析 | 暂不实现 | 先定义保证和必要语义事实，再决定是否扩充 IR |

MMIO 必须定义单次访问宽度与设备顺序；原子必须定义内存序及机器协议；外部调用的保守内存副作用不得被将来的优化器忽略。把代码移到汇编不免除这些合同。

函数指针需要具体签名、间接调用 ABI 和分析策略。目标不可确定的调用对 Blocking 必须是 Unknown，不能默认为 Verified。首版不为未来分析预留全部语义事件，也不承诺跨版本分析插件兼容。

SOS 当前实现及其架构方向是独立工作范围。本方案先定义编译器的移植边界，不等于立即改写现有内核；Linux-user 固定点与 SOS 内自举分开验收。

## 8 实施顺序与交付物

| 阶段 | 依赖 | 交付物 | 必须通过的门槛 |
| --- | --- | --- | --- |
| P0 冻结与记账 | 无 | 当前源码/依赖身份、B、行为变化清单、基线计量 | 干净重建可复现；不把未提交维护源码错记为旧 HEAD |
| P1 执行语义试点 | P0 | 在 B3.1 实现语言上开发 P；新赋值顺序、调用式 defer、显式错误传播试点 | 行为顺序及清理边界正确；确认通用 capture/replay 可删除 |
| P2 声明与阶段分离 | P1 | HeaderSyntax、独立绑定/布局、统一表达式解析、InitData | 布局/常量求值不调用扫描器；语言级依赖环拒绝 |
| P3 数据建模与所有权 | P2 | 具体变体实现、不同 ID 类型、私有表接口、函数生命周期入口 | AST/IR/结果类型试点与总成本账本通过 |
| P4 新源码自举 | P3 | Q、E0/E1/E2/E3、冻结引导包、S-next 版本参考 | 新源码完整固定点、独立行为与目标检查通过；Rust 无新语义补丁 |
| P5 系统切片验证 | P4 | 页分配/页表、文件回滚、设备访问与完整程序实验 | 必要机器能力逐项验收；库和应用成本没有被隐藏 |

P1 至 P3 是构建 P 的过程，部分新规则在对应阶段才可运行，不宣称每个中间候选都已自举。中间试点可以使用暂存的具体错误记录；到 P4 必须符合第 3 节完整新规则并清除临时双路径。

产品源码按阶段串行整合；语义样本、成本测量和独立审查可并行准备。每个阶段记录候选哈希、变更规则、证据与结论；上游语义变化后，依赖它的下游验收失效并重跑。

旧的 91 项回归逐项标记为“保留规则”“明确改变规则”“对应能力删除”，不得用统一删测试替代迁移。保留规则继续验证；改变规则写入新的独立期望；删除能力增加拒绝用例。新语言没有旧源码兼容性通过率指标。

## 9 验收样本与故障检查

| 样本 | 区分力要求 |
| --- | --- |
| 赋值副作用 | index 与 RHS 分别写入日志；RHS 修改索引变量后仍写入先前确定的目标；越界先于 RHS 副作用发生 |
| 实参快照 | 后续参数修改前一参数来源；标量和聚合均观察到约定的旧值 |
| defer | 注册后修改变量、条件分支、循环、break/continue、提前 return、清理函数 panic；注册失败不加入半条调用 |
| 错误与资源 | 第二次申请失败时释放第一次资源；读失败后仍关闭文件；close 失败策略可观察 |
| 类型与标签 | 不同 ID 不能混传；错误载荷、遗漏标签、重复标签、非法 zero、按值递归拒绝；指针递归接受 |
| 常量与布局 | 拒绝布局查询进入数组长度；导入环、按值循环、整数溢出及零重复中的非法初始化分别检查 |
| 存储与阶段 | 编译相邻两函数、故意降低容量、前函数 ID 误用检查、后端不写语义表、诊断位置不依赖最后一次 token |
| 机器与映像 | 窄整数、聚合传参与返回、超寄存器参数、复制重叠、符号缺失、错误重定位和失败输出清理 |
| 自举 | 干净引导、多代完整固定点、源码扰动、空 PATH、目标栈与内存预算、输入/执行日志 |
| 系统 | 位图分配器与页表编码、真实目标上的设备访问和原子协议；不能只以模拟的普通内存访问代替 |

行为测试使用可观测结果和独立期望。对于刻意改变的求值规则，旧编译器输出不作为新规则的正确性判据。引用旧验收只能证明对应旧规则，不自动继承为 S-next 证据。

## 10 预算与停止条件

第一轮生产编译器预算暂定不超过当前约 8,000 物理行，争取接近 6,000 行。计入词法、解析、语义、IR、直接后端、汇编适配、ELF、驱动及选入主线的 Blocking；通用运行支持和平台层另列且纳入交付总账。这是原型预算，不是已测量的净删除预测。

同时报告源字节、非空非注释行、全局写入入口、跨阶段可变依赖、枚举/指令的必改位置、目标静态空间与实际表最高计数。不通过压行、移文件或将具体算法藏入生成物满足预算。

首版继续以目标静态数据与映像不超过 64 MiB、1 MiB guest 栈完成自编译为硬门槛。容量可调整，但必须公开合法输入的新限制；不能把单帧统计当作调用链峰值证明。

出现以下情况应暂停该阶段整合，给出可比较的修订方案：

- 变体与具体错误类型显著增加编译器、库和样本的合计成本，且没有减少可说明的错误面。
- 简化静态初始化导致应用重新实现复杂构造框架，或者需要隐含的自动初始化顺序。
- 显式状态退化成所有函数都接收巨型上下文，或公开接口继续允许任意模块修改内部表。
- 需要让 Rust 与 Q 长期同步新语义才能继续开发。
- 自举稳定却不能独立解释样本行为，或必要的系统操作必须通过未记账宿主服务完成。

阶段通过后的读者应能沿源码追踪：一个名字何时绑定、一个类型何时完成、一次作用域退出执行哪些调用、一个临时 ID 何时失效、一个运行时检查如何成为机器指令。以这些问题是否容易回答，结合整个交付账本判断方案是否成功。

## 11 当前保留的原型决策点

| 决策点 | 默认采用 | 必须提供的反证或确认材料 |
| --- | --- | --- |
| 具体变体替代固定 Result | 是 | AST、IR、三类 I/O 结果及回滚样本的合计规模、布局与诊断成本 |
| 调用式 defer | 是 | 与完全显式清理的应用对照，验证保存参数和错误处理负担 |
| 局部单向定型 | 第 3.7 节规则 | 正反例能用同一规则解释，无默认类型/回溯分支 |
| 有限静态聚合与 zero | 第 3.5 节规则 | 编译器表初始化、变体 arena 与平台数据的实际样本 |
| 类型化 AST/IR 的存储形式 | 具体标签记录，按 ID 引用 | 最大载荷导致的空间增长；必要时可拆分具体载荷表，不引入通用对象系统 |
| 新机器能力 | P5 按样本加入 | 目标指令、ABI、排序合同与真实运行证据 |

默认选择作为原型输入；若证据要求改变语言承诺，应先更新本方案、变化清单和关联验收，再继续整合。正式版本参考在 P4 依据实际接受集编写，不直接把本文转成“已支持功能”页面。
