# Core 实施 workflow 与验收门槛

本文件执行 [交付需求](core-delivery.md) 和 [架构设计](compiler-design.md)。2026-10-06 用户授权开始实施，并指定 GPT‑6.1‑sol 子代理尽可能并行。Extend 首版按已提出的进程内只读接口执行，稳定外部 IR 协议不在本轮范围。

## 并行规则

当前并发容量为主代理加三个子代理。主代理维护共享契约、语义流水线与最终集成；三个 GPT‑6.1‑sol 工作者按文件所有权推进，完成当前任务后继续领取无冲突工作。共享工作区无需搬运补丁，修改即时可见。

| 工作流 | 首批文件所有权 | 后续工作 |
| --- | --- | --- |
| 语法与解析 | `src/syntax/`、固定 Unicode 数据、`resolve`、`check` | 类型推导、泛型／常量与模式、前端覆盖 |
| 类型与目标 | `src/types.rs`、`layout.rs`、`abi.rs`、`linkage` | `src/target/` 与 C／原子／MMIO／陷阱集成验收 |
| 平台与扩展 | `runtime/`、`platforms/`、`lower`、平台夹具 | `src/extend.rs`、真实元数据接口与总验收入口 |
| 主代理 | `source`／`diagnostic`／`ir`／`hir`、驱动、工作流 | 独立规范审计、集成、清洁重建与最终覆盖审查 |

公共数据结构先落地并通知消费者；需要变更时向其所有者提出，不能同时改写同一文件。任务报告必须列出实际命令、结果、未覆盖范围；实现限制以 `I_UNSUPPORTED`／`I_LIMIT` 显式报告，不能冒充规范拒绝。禁止根据测试文件名、manifest 预期或特定源码文本生成结果。

每轮执行：读取规范条款 → 确定输入／输出与所有权 → 实现 → 有区分力的测试 → 主代理集成 → 执行相关验收 → 更新剩余缺口。发现失败先定位所属阶段；只重跑受影响及必要回归，不通过放宽预期掩盖问题。

## Gate 与通过条件

| Gate | 通过条件 | 证据 |
| --- | --- | --- |
| G0 工程与平台 | Rust 构建；手写夹具进入 S-mode；正常、panic、平台故障与超时可区分 | `cargo test`；`tools/test_runtime.py` |
| G1 语法／模块 | 完整语法与固定 Unicode 15.1；所有适用语法例；模块输入顺序与可见性 | syntax／resolve 集成测试 |
| G2 Core 静态语义 | 所有 76 项适用的 Core 接受／拒绝符合规范；泛型、布局、常量及诊断完整 | conformance 的静态结果与新增条款测试 |
| G3 普通目标执行 | 27 run、4 panic 在编译器生成的 RV64 ELF 上符合结果；新增整数、聚合、退出例 | QEMU 协议、构建命令、IR／汇编留存 |
| G4 目标专项 | C ABI 双向、重定位／链接失败、原子多 hart／映射、真实设备 MMIO、完整 trap | 独立 C／汇编夹具＋编译器端到端测试 |
| G5 Extend 接口 | 元数据实际可读、依赖校验、四态、严格门禁、机器事实与失效条件 | 接口探针；不得称真实验证器通过 |
| G6 可复现完整交付 | 上述全通过、条款覆盖闭合、清洁环境复现、示例与用户文档 | 固定版本／依赖、完整报告及已知限制审计 |

一个 Gate 部分通过只能报告具体通过项。当前 manifest 是基线而非语言全集；G2／G3 通过不意味着 G4 或 G6 完成。未实现、跳过、崩溃、无报告、工具缺失与超时均不能计为通过。9 个 Extend 用例只执行 Core 接受检查，真实验证器预期记录未提供。

最终专项矩阵必须覆盖：多文件模块顺序；C ABI 超八标量及 1／2／大于 2 XLEN 聚合、寄存器栈拆分、回调与隐藏返回；聚合实参逐个快照；packed 和 4096 对齐；外部静态及纯地址边界符号；原子全部操作和合法顺序、窄原子邻接存储、强 CAS 重试；设备允许宽度上的访问次数与 fence；x1—x31／sepc／sstatus、entry 与 handler defer、重复及嵌套陷阱；缺失运行符号拒绝。

## 进度记录原则

实施状态与测试证据由实际产物及测试报告确定。文档中的设计草图不是已实现声明；手写平台探针不是编译器执行证据；接口假分析不是 Ownership／Borrow 验证器。主代理完成相关工作后更新 README 与交付说明，最终只在 G0—G6 均满足时声明完整 Core 交付。

条款追踪数据维护在 [core-coverage.json](core-coverage.json)。完整验收会校验每个条款的实现路径、关联用例／Rust 测试实际通过结果、审查状态和剩余缺口；缺少其中任一项不能得到 `complete_Core_delivery: true`。清洁重建另从不含 `target/` 和 `build/` 的源码副本编译，使用已有宿主工具与 Cargo 下载缓存，并重复运行验收及比较目标 ELF 摘要。
