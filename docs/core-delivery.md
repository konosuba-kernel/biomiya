# Core 完整交付需求

本文件定义工程交付与验收，完成度以实测验收为准。语言基线为 [reference 0.5](reference.md)，目标基线为 [rv64-core-v1](architecture-rv64.md)；实现结构见 [compiler-design](compiler-design.md)。实施审计发现的块式语句解析歧义已在 reference 第 3.1 节明确规则，未用测试适配器另设语义。

## 1. 决策记录

| 项目 | 决策 | 状态 |
| --- | --- | --- |
| 产品目标 | 完整交付 Core，保留 Extend 扩展接口 | 用户已确认 |
| 实现语言 | Rust | 用户已确认 |
| 首版后端 | 直接生成 RV64 汇编，首版不追求优化 | 用户已确认 |
| 配套交付 | 启动代码、链接脚本、panic／陷阱运行时、QEMU 自动验收 | 用户已确认 |
| Extend 实现范围 | 先提供进程内分析接口、语义视图、结果协议及接口验收，暂不实现验证器 | 按用户授权的当前方案实施 |
| 外部 IR 协议 | 调试 dump 可提供，版本化、可由外部工具稳定读取的 IR 文件协议暂不纳入 | 本轮不纳入 |

已采用的工程配置：首个受支持宿主为 Linux x86_64；汇编与链接使用 Clang 集成汇编器和 LLD；参考运行平台为 QEMU `virt`；完整性与可读性优先，源码行数作为统计指标而非删减功能的硬上限。编译器本身可使用 Rust 标准库，目标程序的运行支持不依赖宿主 libc、堆分配、GC 或异常展开。

## 2. 交付边界

“完整 Core”表示 reference 正式部分第 1—28 章、附录所列语法与内建表面，以及目标补充 R1—R9 全部落实；不是把现有测试通过数作为功能定义。Core 模式默认关闭所有 Extend，按规范接受未获所有权、借用或阻塞证明的程序，仍执行规定的类型检查、unsafe 检查和运行时 panic。

| 编号 | 必须交付 | 验收证据 |
| --- | --- | --- |
| C01 | UTF-8／Unicode 15.1 词法、完整语法、属性及诊断 | 正反例；Unicode 固定数据版本；错误位置 |
| C02 | 多文件模块、可见性、前向引用、别名、内建名字与遮蔽 | 输入顺序置换；冲突和私有访问负例 |
| C03 | 全部 Core 类型、局部推导、Copy／resource 分类、方法与泛型 | 未使用泛型与不可达代码边界；实例缓存顺序无关 |
| C04 | 确定布局、常量求值、静态对象、地址重定位 | RV64 布局表；循环／溢出拒绝；ELF 与运行结果 |
| C05 | 全部表达式、模式、循环、Result／`?`、defer、临时存储 | 求值顺序；所有退出路径；嵌套穷尽性检查 |
| C06 | 普通 ABI、完整 LP64 C ABI、函数指针及跨对象链接 | 与独立 C 对象双向调用；寄存器／栈边界；聚合快照 |
| C07 | 引用、原始指针、四种地址空间、切片、未初始化存储 | 原始取址无读取；packed；零大小；权限／unsafe 负例 |
| C08 | 全部整数运算、转换、边界与算术失败、显式 panic | 各位宽边界；常量／运行语义一致；目标 panic 可观测 |
| C09 | Atomic 全部合法载荷与操作、顺序检查、volatile／MMIO | 多 hart 用例；原子映射审查；设备访问轨迹与 fence |
| C10 | 特殊函数、陷阱转移、CSR、受限汇编、架构内部函数 | 完整寄存器恢复；cleanup 顺序；嵌套策略；汇编约束 |
| C11 | 命令行驱动、ELF 构建、依赖报告、参考平台与示例 | 从干净环境按文档构建并运行；故意移除依赖时失败 |
| X01 | Extend 接口与信息保留，明确报告未验证 | 接口探针与结果协议测试；不冒充真实验证器 |

每项在实施中继续细分为“规范条款 → 实现模块 → 正例／反例或目标夹具 → 实测结果”的追踪记录。新发现的规范歧义单独记录并修订规范，不在代码中悄悄定义另一种语言。

本轮不包含 Ownership／Borrow／Blocking 等验证算法、额外目标、优化器、自举、包管理器、LSP、通用操作系统库或生产内核。标准内建类型和接口属于 Core，必须实现；通用分配器、文件系统和调度器不属于本轮。`rv64-core-v1` 的陷阱处理中不睡眠、不调度、不主动开启中断；更广的内核平台能力需要另行命名的平台配置。

## 3. 使用与产物合同

命令行已实现，完整选项见 [构建与运行](building.md)：

```text
biomiya check --target rv64-core-v1 [--diagnostics json] <显式源文件列表>
biomiya build --target rv64-core-v1 --emit asm|obj|elf -o <产物> <显式源文件列表>
biomiya build --platform qemu-virt-core-v1 -o kernel.elf <显式源文件列表>
```

`check` 检查全部非泛型函数及规范要求的具体实例，不要求外部符号已有实现。`asm`／`obj` 输出允许尚待链接的外部符号；`elf` 必须完成依赖、目标兼容性及链接检查。显式指定 ELF 运行平台后，驱动选择随附运行对象与链接脚本；也允许用户显式提供自有平台对象和脚本。平台名是工程配置，不是新语言目标。没有隐式 `main` 或自动搜寻目录模块。

编译库与命令行分离。诊断提供规范类别、源码范围、相关位置及泛型实例化路径；区分 Core 错误、验证失败、工具链／执行基础设施失败和编译器内部错误。尚未实现必须报告 `I_UNSUPPORTED`，不能借某个规范错误类别让负例“通过”。

构建报告记录编译器／reference／目标版本、输入和平台文件摘要、完整工具命令及版本、导出与运行依赖符号、分析启用状态。用户可以保留汇编、对象、链接 map 和调试 IR，以定位跨阶段问题。IR dump 首版只供调试，不能未经另行约定就当稳定工具协议。

可复现交付要求提交 Rust 工具链版本、Cargo.lock、Unicode 数据版本与来源、外部工具版本／获取方式，以及固定的 QEMU 配置。验收必须从干净检出和明确依赖开始；在同一锁定环境重复构建比较产物摘要，排除时间戳和随机遍历顺序。不承诺跨不同工具版本得到相同字节。

## 4. 验收层次

当前 [manifest](../tests/conformance/manifest.json) 有 76 项：27 run、4 panic、4 accept、32 reject、5 extend-reject、4 extend-accept。这里记录规范预期；运行报告另外记录实际编译及 QEMU 结果。

Core 交付要完成前 67 项的完整协议，并对 9 个 Extend 用例执行 **Core 接受检查**；其中可能违反动态合同的用例不运行。相应真实验证器尚未实现时，其验证预期记为“未提供”，不可计入验证通过率。接口探针只证明信息和调用协议可用。

| 层次 | 检查内容 | 失败判定 |
| --- | --- | --- |
| 前端 | 76 项的适用 Core 检查、新增条款正反例、文件顺序置换 | 错误类别错误、崩溃、误拒合法程序、漏查不可达代码均失败 |
| 语义 IR | 求值次序、位置和移动、隐式适配、cleanup、效果信息 | 丢失规范信息或不同阶段重复解释语义均失败 |
| 目标执行 | 27 个 run 与 4 个 panic，加新增算术／聚合边界例 | 真正编译并执行 RV64 ELF；超时不能算 panic |
| ABI／链接 | 独立 C 交叉调用、外部静态、重定位、缺失符号、节／对齐 | 普通 ABI、C ABI、运行时入口分别验证 |
| 平台 | 启动、多 hart 原子、MMIO 设备观察、IRQ／trap、嵌套故障 | 对照 [补充验收](conformance.md) 全项，不能以 RAM 或前端检查代替 |
| Extend 接口 | 只读视图、依赖校验、四态报告、语义及机器信息、失效条件 | 关闭时不得误称验证成功；未知严格验证不能放行 |
| 复现 | 干净构建、目标示例、一条验收入口、日志／版本归档 | 隐藏依赖或不可复现步骤必须解决 |

目标执行使用明确区分 PASS、PANIC、平台故障、超时的测试协议，记录测试 ID 和结果。最终统计不得把 skip、未实现或超时归为通过。原子测试还需核对指令映射及其模型依据；多次未观察到错误不能单独作为内存模型证明。

最终演示至少包含：多文件 Core 程序；与 C 双向调用及外部数据；原始存储和切片初始化；可恢复陷阱／IRQ 的最小内核程序；多 hart 原子通信。示例、运行对象和命令均在仓库中维护。

## 5. 实施里程碑

| 阶段 | 产出与退出条件 |
| --- | --- |
| M0 工程与平台闭环 | Rust 库／CLI／测试入口；工具链固定；手写探针在 QEMU 进入 S-mode，正常退出与 panic 可区分；确认多 hart 启动和 MMIO 观测办法 |
| M1 最小编译执行闭环 | 源位置、解析、解析后的声明、基础类型、IR、栈槽后端贯通；由编译器生成的算术／分支／函数调用在目标运行 |
| M2 完整前端与静态语义 | C01—C04 的全部检查、泛型／模式／常量闭合；Core 静态用例通过；建立条款追踪表 |
| M3 完整普通执行 | C05—C08；所有普通表达式、聚合、退出清理、函数指针、完整 C ABI；相关运行及互操作夹具通过 |
| M4 完整目标与运行支持 | C09—C10；原子／MMIO／汇编／陷阱及补充集成验收全部完成 |
| M5 扩展接口与最终交付 | X01 接口探针、C11 复现与文档、全套验收报告、覆盖缺口归零 |

阶段用于尽早暴露风险；M1 的可运行子集不改变完整 Core 目标。Extend 需要的信息从 M1 的 IR 起保留，接口探针随相关功能加入，不等到 M5 才改造前端。C ABI、defer、多态递归与高对齐尽早加入针对性例子，避免最后才发现结构需要重做。

实现规模分别统计前端／后端、运行时、测试与夹具、生成数据。优先单个 crate 的清晰模块和显式数据结构；不为满足“数千行”压缩代码、删减检查或把复杂度藏进测试适配器。实际规模和热点在 M2、M4 复评，当前不给未经实施验证的工期或行数承诺。

## 6. 实施与验收状态

仓库现提供 Rust 库及 CLI、语法／名字／类型检查、常量与布局查询、HIR／MIR、RV64 后端、LP64 C 互操作、参考运行时和 QEMU 验收。声明身份、泛型模板与实例、完整表达式／defer、类型适配、原子请求和真实目标信息经进程内只读接口提供给 Extend；默认注册表没有真实验证器。

基线、独立规范审计、机器互操作及平台探针分别运行。最终审查数据在 [core-coverage.json](core-coverage.json)；该文件的 `known_gaps`、各项状态和关联实测证据由总门禁检查。没有完整报告时不能从某一组测试全绿推导完整 Core 已交付。

复现环境固定在 `toolchain-lock.json`。`tools/reproduce.py` 创建清洁源码副本，独立重建并执行 Rust 测试、全部源用例、机器集成与平台探针；使用已安装的宿主工具和 Cargo 下载缓存，不复用仓库编译产物。还比较独立重建的示例 ELF 与原构建的字节摘要，并在 QEMU 运行示例。最终入口是 `python3 tools/accept.py --stage full --json build/acceptance.json`。

实现规模按手写编译器、生成 Unicode 数据、运行时和测试分别统计。当前工程采用显式模块边界，未为追求行数删去规范检查或把语言执行隐藏在测试适配器中。首版不优化；其栈槽策略和参考平台栈配置见 [架构](compiler-design.md) 与 [运行时](../runtime/rv64/README.md)。

2026-10-07 的交付统计按物理行计，包含注释与空行：手写编译器 Rust 共 30 个文件、18,430 行；固定 Unicode 表另有 2,096 行，平台／运行时 C、汇编和链接脚本共 357 行。Rust 测试 3,399 行，语言夹具 2,481 行，另有 Python 验收工具及 C／汇编互操作夹具。首版没有实现“数千行内完整 Core”的规模预期；局部结构推断、泛型常量、完整诊断和目标互操作是实际复杂度的一部分，不能仅以最短可运行子集估算。
