### 真实硬件、内存与资源路径

读取全部 `system.vt`、`file_rollback.vt`、两个 syscall 适配器、monitor、加载器和测试驱动，并独立反汇编 monitor，记录为 `build/snext-p5-independent-r1/monitor.disassembly`。

- UART 位于 QEMU virt 的实际 16550 MMIO 地址 `0x10000000`；`lbu` 读取 LSR 偏移 5 的 bit 5，`sb` 写 THR，写入前后均执行 `fence iorw,iorw`。它不是把设备寄存器替换成普通 RAM。
- QEMU 启动参数实际为 `-machine virt -cpu rv64 -m 128M -smp 2 -bios none`。hart 0 发布 payload 后用 `amoswap.w.rl` 发布请求；hart 1 用 `amoswap.w.aq` 获取请求，再读 payload、写响应并 release 发布完成；hart 0 用 `amoadd.w.aq` 等待响应。下一请求的 release 也将上一轮完成标志清零排在发布前。4096 轮逐项检查 `result == input + 17`，没有把普通 volatile 读取当作原子同步。该固定单生产者协议不是通用并发库，QEMU 执行也不是实体硅片压力证明。
- Sv39 使用 level-1 的 2 MiB 叶子，低 64 MiB 映射到物理 `0x81000000` 起始区域；分配池的 16 个 PageId 对应真实 `[0x85000000,0x87000000)` RAM。原样本经 alias 和 direct 地址双向读写，超出仅“读回 PTE”的弱验证。
- 独立组合探针把可用位改为第 15 位，实际分配 `0x86e00000`，再将相同虚址从 page 15 重映射到 page 14：新别名读写正确，旧物理页数据保持原值。完整程序仍完成 4096 次交换，UART 输出 `P5 OK\n`，退出 0。验证了较高位分配、实际物理地址和 `sfence.vma` 后的新映射。源码、编译命令及机器运行记录在 `build/snext-p5-independent-r1/upper-remap/`、`probes.json`。
- 对文件切片独立执行 `qemu-riscv64 -strace`：`openat(...,"/dev/null",O_WRONLY)=3`，`read(3,NULL,0)=-EBADF`，defer 的 `close(3)=0`，再次关闭及清理策略测试均得到 `-EBADF`，最终退出 0。证据在 `file-strace.log`；并非模拟资源计数器。

### 阻断问题：页表高位通过了地址范围检查

`monitor.S` 的 install 路径先对 `a1` 右移 10，再左移 12 得到物理地址。该转换等于对部分值左移 2 并截断，PTE 高两位会消失；只检查低 10 位 flags、对齐和截断后的 RAM 地址不能排除非法高位。

独立源构造：

```vt
let pte:usize = ((0x85000000_usize >> 12_usize) << 10_usize)
    | 199_usize | 0x8000000000000000_usize;
unsafe { let accepted:usize = p5_install(64,pte); }
return 7;
```

按此平台的受限 Sv39 合同应在 install 处 fault，退出 250。实际返回调用者并退出 **7**。记录为 `build/snext-p5-independent-r1/pte-high-reserved/machine/verification.json`，其中 `accepted: false`、期望 250、实际 7；原始 ELF 由同一个 E3 构建。该平台没有承诺 Svnapot/PBMT 扩展语义，不能把高保留位默认为新的编码能力。

需要由实施者显式验证 Sv39 PTE 的高保留位或保证解码物理地址无截断，并纳入新负例。修改 monitor 或测试输入后产生 r2 候选，重编译运行并保留 r1 失败证据；不能仅放宽本探针预期。
