# 编译器代码成本审计

审计日期：2026-10-09。对象为提交 `8feff82b1e9ae58ada07975339b071f88feb27e7` 下的 Core 0.5 编译器，以及工作区中独立的 Core S 原型。目标是判断这些代码为什么存在，以及哪些成本适合 konOSuba 的教学主线。本次没有修改语言规范或编译器实现。

**主要结论：Core 0.5 的规模主要由语言语义及其组合产生。扣除生成数据后，18,237 行有效代码中，语义检查和类型布局占 52.7%；ABI 与 RV64 后端占 9.3%。保留 0.5 全部承诺，仅整理实现，没有证据能把它缩到数千行。**

Core S 原型已将直接依赖在内的手写有效代码缩到 4,552 行，但它不是同等能力的替代品。它证明了收窄语义后可以形成较小的实现，尚未证明完整 Core S、内核应用与自举的最终成本。

## 实际编译路径

主路径在 [driver.rs:236](/home/mii/code/konOSuba/biomiya/src/driver.rs:236)：

```text
显式输入源文件
  → syntax::parse
  → check::check
       Resolver、声明、模板、推导、具体实例、常量、布局准备
  → 带类型的 HIR
  → lower::lower
       求值顺序、快照、清理、模式、显式控制流、语义事件
  → CFG IR
  → target::rv64::emit
       栈槽、调用约定、指令、数据、运行时检查
  → toolchain::build
       外部 Clang 汇编、LLD 链接、目标格式检查
  → 目标事实与可选分析报告
```

`check` 命令在 HIR 阶段结束，`build` 才继续降低与发射。编译器没有把源码交给 LLVM 优化，也没有自己实现完整汇编器和链接器。当前后端以栈槽和少量临时寄存器为主；两万行并不是由复杂优化器造成的。

分层本身有用途：AST 保留源码写法，HIR 保留已解析的类型和结构，CFG 明确分支与清理顺序，后端处理机器细节。三种表示的定义文件 `ast.rs`、`hir.rs`、`ir.rs` 合计只有 720 行有效代码。不能把全部规模归因于“IR 太多”；真正昂贵的是每层需要解释多少语义。

## 主要成本及其必要性

### 类型推导增加了一套结构求解

`check/inference.rs` 有 1,359 行有效代码。它包含类型变量、统一、出现检查、字段投影延后求解、字面量默认类型，以及元组、数组、函数、引用、泛型构造和模式的结构传播。

[expressions.rs:3](/home/mii/code/konOSuba/biomiya/src/check/expressions.rs:3) 先调用 `prepare_inference`，再进入正式表达式检查。推导器在 [inference.rs:69](/home/mii/code/konOSuba/biomiya/src/check/inference.rs:69) 遍历、求解并按源码位置记录类型提示；正式检查仍要检查合法性并生成 HIR。

例如现有测试接受不同分支中的 `(1_u8, 7)` 与 `(2, 3_u8)` 共同推导出元组类型，泛型实参也参与约束。这已经超出“从显式初始化器得到局部变量类型”的简单机制。[测试入口](/home/mii/code/konOSuba/biomiya/tests/inference.rs:6)

**判定：属于便利性语义的主要成本，适合从极简教学主线中收窄。** 显式局部类型、显式泛型实参，或者只允许已知期望类型向子表达式传播，可以减少求解需求。仅要求函数签名显式，不能消除这个推导器。

这里的 1,359 行是专属实现的体量，不是可直接净删的体量。调用适配仍要保留或重写；保留现有推导规则时，两次遍历有真实职责。

### 泛型与依赖布局引入延迟语义

泛型成本分散在 `types`、`check/mod`、`names`、`calls`、`inference`、`deferred` 和 `layout`。不能只找到一个泛型函数然后据其长度估算。

[check/mod.rs:751](/home/mii/code/konOSuba/biomiya/src/check/mod.rs:751) 的 `instance` 维护实例缓存、活动实例、实例依赖图、Copy 约束以及多态递归拒绝。未实例化模板还要经过名字和模板体检查。[names.rs:243](/home/mii/code/konOSuba/biomiya/src/check/names.rs:243)

更重的交叉来自数组长度依赖泛型类型布局。例如 `struct B<T> { bytes: [sizeof(T)]u8 }` 需要在类型具体化后求长度；0.5 又允许其中出现常量块、局部绑定和条件表达式。于是 [deferred.rs:7](/home/mii/code/konOSuba/biomiya/src/check/deferred.rs:7) 保存原始 AST、定义环境、泛型绑定和查询依赖，在 [prepare_length](/home/mii/code/konOSuba/biomiya/src/check/deferred.rs:152) 中恢复具体环境并重新求值。

这解释了 `deferred.rs` 的 572 行为什么存在：它维护的是延迟表达式的名字、可见性、类型与求值语义。直接删掉会破坏当前合法程序。

**判定：这是最值得成组收窄的承诺之一。** 取消用户泛型、依赖型数组长度和原 AST 重放，会比单独删方法语法影响更多成本来源。代价是库和应用需要更多具体类型与重复实现，应连同几项真实内核数据结构一起核算。

### 常量语言已经需要独立执行机制

`check/constants.rs` 有 1,248 行有效代码，其中不只有整数常量折叠，还包括常量合法性、块内环境、条件、模式匹配、聚合构造与相等、字段和索引、地址及静态数据序列化。

[constants.rs:345](/home/mii/code/konOSuba/biomiya/src/check/constants.rs:345) 的 `reduce` 处理块、绑定、条件和匹配；[layout.rs:437](/home/mii/code/konOSuba/biomiya/src/layout.rs:437) 又对 `ConstLen` 进行带位宽、溢出和转换规则的求值。它们处理不同表示，不能简单认为是两份完全相同的代码，但需要保持相同算术规则。

现有 [const_parity 测试](/home/mii/code/konOSuba/biomiya/tests/const_parity.rs:4) 将 40 种表达式分别放进普通常量与泛型依赖上下文，共检查 80 个场景。这直接体现了组合规则的维护成本。

**判定：保留常量和静态数据能力，收窄编译期可执行的语言。** 明确类型的标量常量、有限算术、`sizeof/alignof` 和必要的静态初始化有系统用途；常量块、模式匹配和复杂构造是否进入首版，应单独论证。即使取消泛型，仍必须检查常量与布局之间的循环依赖。

保持 0.5 语义时，可评估共享整数运算判定和减少中间表示，但这属于需要验证的重构机会，不能承诺按文件大小删除。

### 引用与资源语义已经付费，完整验证尚未交付

当前类型层维护 Copy/resource、引用可变性、地址空间和类型属性；表达式检查维护位置、只读访问、隐式适配和非 Copy 值限制。降低阶段区分观察、复制、移动、借用与再借用，记录完整表达式和存储生命周期。

证据见 [lower.rs:210](/home/mii/code/konOSuba/biomiya/src/lower.rs:210)、[ir.rs:133](/home/mii/code/konOSuba/biomiya/src/ir.rs:133)。这些不是完整借用检查器；Core 已实现部分语义与合法性检查，但真正的 ownership、borrow、blocking、concurrency、kernel 分析注册项仍是 `implementation: None`。[extend.rs:259](/home/mii/code/konOSuba/biomiya/src/extend.rs:259)

`extend.rs` 自身为 689 行有效代码，成本还分布在 HIR、IR、降低、驱动和目标事实采集。后端对 `InstructionKind::Event` 不发射指令，但这只表明事件是元数据，不意味着制造这些事件所需的类型和求值规则可以删除。[后端事件处理](/home/mii/code/konOSuba/biomiya/src/target/rv64.rs:755)

**判定：需要明确主线到底提供哪些保证。** 如果主线采用普通值复制和显式资源协议，可以不同时维护旧的引用/移动语义与完整分析扩展契约；应保留源码位置、类型、基本控制流和必要诊断。资源泄漏、重复释放和初始化责任随之转移到库与使用者，必须作为真实代价说明。

删除 Extend 注册框架不会自动删除引用语义；保留全部语义却关闭分析开关，也不会显著缩小编译器。

### 控制流与清理中的大部分代码有直接用途

`lower.rs` 为 2,134 行有效代码。它负责把语言的求值顺序转成明确的机器执行顺序，包括短路、循环、返回、参数快照、聚合复制、索引检查、模式、`?` 和 `defer`。

例如先计算返回值、再运行 defer，是防止清理过程改变返回结果的必要顺序；先保存第一个实参，再计算可能修改它的第二个实参，也是确定的语言语义。不能为了减少临时槽而悄悄改变这些行为。

[cleanup](/home/mii/code/konOSuba/biomiya/src/lower.rs:289) 按反向作用域和注册顺序展开清理；[try_value](/home/mii/code/konOSuba/biomiya/src/lower.rs:1803) 处理错误传播；[patterns.rs:302](/home/mii/code/konOSuba/biomiya/src/check/patterns.rs:302) 实现递归模式矩阵的穷尽性判断。

**判定：保留显式控制流和正确的求值、清理规则，缩小需要组合的语法。** 语句式分支、无返回值的循环、浅层模式、受限 defer，可以降低成本。`?` 和 defer 不能按“只是语法糖”忽略，也不必默认全部删除；应以错误路径与资源回收代码的总量评估。

Core S 的检查器已经直接生成 typed CFG，并在注册 defer 时生成片段、出口实例化片段。这是具体的结构简化尝试，但仍需处理槽和块编号重映射，不能把这类成本归零。[Core S 清理](/home/mii/code/konOSuba/biomiya/core-s/src/check.rs:322)

### 现代目标的必要成本存在，但不是规模主因

ABI 与 RV64 发射共 1,695 行有效代码。参数、返回值、栈对齐、大偏移、整数位宽、聚合复制、trap、MMIO 和运行时检查都有直接的系统用途。

额外的范围包括 C 聚合按值传递、任意大对齐、packed 访问、窄原子和多种内存序，以及灵活的内联汇编。能否缩减取决于教学主线是否需要这些变体，而非它们是否“专业”。[ABI 分类](/home/mii/code/konOSuba/biomiya/src/abi.rs:192)、[目标内建](/home/mii/code/konOSuba/biomiya/src/target/rv64.rs:976)

**判定：保留一种确定的内部 ABI 和最小硬件访问机制。** 首版可评估 C 互操作仅支持标量与指针、限定对齐、限定原子宽度和内存序。不能删除实际使用的 MMIO 宽度与顺序保证，也不能用一段未计数的 C shim 隐藏复杂度。

即使保留较多现代目标规则，后端也不是首先应大幅重写的部分。

### 工具支持与名字兼容可以收窄，但收益有限

驱动、工具链、链接名字等共 1,361 行有效代码。其中包含必要的输入、工具调用、产物、错误与运行依赖处理，也有更宽的承诺：多种发射模式、详细摘要、扩展报告、伴随文件，以及字节级外部名字支持。

[linkage.rs](/home/mii/code/konOSuba/biomiya/src/linkage.rs:1) 为无法直接放入汇编文本的合法符号/节名字节建立别名，并恢复 ELF 名字；这些规则进一步进入驱动、工具链和后端。把外部名字限定为一个明确的小字符集，可以删除一组兼容分支，但必须改变对应输入合同。

**判定：可按单一教学构建路径收窄，不应删掉失败报告和可复现的调用参数。** `diagnostic.rs` 本身只有 37 行，但实际诊断代码散布于检查点，因此不能把 37 行说成全部诊断成本。

即使假设将 Extend 和驱动工具链两组整组扣除，手写代码仍有 **16,187 行**；而这两组实际上还有不可缺少的工作。仅整理外围无法兑现数千行目标。

## 可在保持语义时评估的重构

以下是实现结构上的机会，与上文需要改变语言承诺的删减分开处理。

| 发现 | 源码证据 | 建议与限制 |
| --- | --- | --- |
| 聚合相等有两条展开路径 | `lower.rs:1840` 的 `equal/enum_equal`；`target/rv64.rs:1170` 的发射回退 | 普通源码路径先降低；直接构造 MIR 的调用者仍可要求后端比较聚合。可统一规范化入口，但回退路径有独立测试和文档承诺，不能当死代码删除。 |
| 布局引擎的缓存生命周期很短 | `LayoutEngine::new` 创建空缓存；lower、ABI、常量和目标报告反复创建引擎 | 可在类型具体化后保存已验证布局，让后续阶段只读取。0.5 类型仍会定义、替换和实例化，缓存有效性必须明确；尚未测量编译耗时收益。 |
| 多处维护整数语义 | HIR 常量求值、ConstLen 求值、降低、RV64 发射 | 可共享运算分类和规则测试；不同阶段的执行方式仍然不同，不宜为追求共享引入一个更复杂的通用执行框架。 |
| 不同遍历反复识别表达式结构 | 推导、名字、依赖查询、正式检查、降低 | 在明确仍需哪些遍历后，合并重复的无状态收集；有期望类型、求值顺序、可见性和模板模式差异的遍历不能机械合并。 |

这几项可能降低维护负担；静态审计没有证明净删行数，更没有证明可以保留全部语义而缩到四分之一。不能把不同文件的范围相加当收益估计。

按物理行计算，相应源码总计为 6,826。两个编译器共享文件，在比较各自依赖闭包时分别计入；计算仓库唯一文件总量时只能计一次。两套实现也不能相加后称为“一个编译器的运行规模”。

本地原型合同明确尚不覆盖模块、导入、多种整数类型、用户枚举、切片、函数指针、静态/外部对象、FFI、MMIO/原子/CSR/asm/trap、字符串和 Extend 等能力。[原型合同](/home/mii/code/konOSuba/biomiya/docs/design/core-s-pilot.md)

本次检查发现 Cargo 声明了 `src/main.rs` 的 CLI，但文件不存在；`tests/frontend.rs` 也未提供。全特性库检查通过，只证明这些库模块可以一起编译，不等于源文件到 ELF 的现成命令链或完整 Core S 已交付。

所以现有数据不能推出“Core S 比 0.5 缩小约 75%，补齐后仍如此”。除了语义删减，它还少了平台能力、工具驱动、部分语言类型和完整集成。逐项补齐的实际增量才有预测价值。

## 面向 konOSuba 的取舍顺序

首先冻结的是语言承诺，不是新的总行数。审计支持以下优先顺序，但不自动修改已经存在的规范：

1. **优先评估收窄泛型、求解式推导与依赖常量这组交叉机制。** 这是最大的语义成本集中区。以几项内核结构和工具程序检验显式类型与具体类型的代价。
2. **明确值、引用、资源与验证的职责。** 如果采用普通复制与显式资源协议，就不同时继承旧引用/移动语义和全部 Extend 契约。需要记录转移到库和应用的代码及风险。
3. **保留一个清晰的执行模型。** 用有类型的控制流表达求值顺序、返回快照、错误传播和资源清理；限制源语言的组合，避免把复杂度重新藏入隐式处理。
4. **限制目标接口的变体。** 一个目标、一种内部调用约定、小型 FFI 合同、确定的硬件访问能力；先不承担全部兼容边界。
5. **再做表示与公共 API 的整合。** 布局结果、聚合相等、整数规则和直接 MIR API 都有收束空间，但只能在语义与入口合同确定后判断。

用于下一次预算复评的实际程序应同时覆盖：固定大小页/块分配结构、句柄表与显式回收、含失败路径的文件操作、小型词法/表达式处理工具、真实 MMIO/陷入入口。它们应使用同一套语言能力；不能为每个程序补一组独有机制后仍称语言范围稳定。

每次增补记录四项：编译器净增量、运行时净增量、库与应用净增量，以及新增跨阶段规则。删除泛型后多写的具体容器、资源责任转入库后增加的显式状态和检查，也计入总账。这里不假定 0.5 已提供自动析构或完整所有权验证。必要的拒绝、错误路径和诊断不能当作可有可无的边角成本。

当前没有足够证据为完整版本给出四千、六千或一万行的可靠承诺；已获得的是一份能解释主要成本、指明下一步应验证什么的账本。

## 验证与复现

cargo test --locked --offline --test inference --test const_parity --test const_constructors --test extend
cargo test --locked --offline --test backend aggregate_equality_ignores_padding_and_inactive_enum_payload -- --exact
