# 语言承诺缩减与参照语言调研

研究日期：2026-10-09。对象为 konOSuba 的教学目标、biomiya Core 0.5、Core S 设计及原型。本文是研究与候选决策，**不修改正式语言规范，不表示新增取舍已经得到用户确认或实现验证**。外部资料使用项目官方文档、源码仓库和课程资料；没有在本地构建这些外部语言，也没有统一测量它们的编译器规模或性能。

## 结论

biomiya 应当承诺：用一套有限、确定、可追踪的规则写出本项目的编译器、内核和应用。暂时不应承诺：成为能够方便地编写任意现代系统软件的通用语言。

真正值得削减的是三类通用性：**任意类型上的代码复用、编译期执行程序、跨表达式和阶段补全语义**。它们分别带来实例化、求值器和求解／延迟检查，且相互放大。删掉几个语法糖不能代替这些决策。

建议以 Core S 为实验底座，但继续收窄常量与布局的依赖、错误传播的位置、平台专用入口及扩展接口；保留模块、具体结构、带标签枚举、数组／切片、明确求值顺序和受限 defer。局部类型省略不必一刀切：从一个已经定型的初始化器取类型，不等于恢复约束求解器。

参照优先级是：**Hare 看语言边界；Selfie 看教学闭环与自举；Austral 看能否负担一种受限的静态资源保证；Pre-Scheme 看宿主调试与目标执行的关系。** Zig、Odin、C3 是可用的系统语言参照，不能因使用体验简洁而推断其实现适合数千行；Virgil、C0、Vale 则展示了把责任放到运行时的不同路线。

## 1. 我们究竟在缩减什么

“语言承诺”包括允许哪些程序、替程序员完成什么、保证什么，以及必须和哪些环境互通。一个关键字很少的语言，仍可能承诺一个复杂的编译器。

| 承诺层面 | 0.5／Core S 中的例子 | 真正要回答的问题 |
| --- | --- | --- |
| 可表达的通用性 | 泛型、依赖长度、常量控制流 | 项目是否真的需要用户定义这些通用机制？ |
| 自动完成的工作 | 推导、默认类型、隐式移动／再借用 | 编译器能否仅根据局部已知事实决定操作？ |
| 运行与安全保证 | 边界检查、复制、资源责任、defer | 删除后谁承担责任，有没有可见的替代机制？ |
| 环境兼容 | C ABI、链接名字、陷阱、原子 | 必须兼容整个生态，还是足以连接本项目的固定平台？ |
| 工具可观察性 | Extend、目标事实、独立 MIR 入口 | 是否已有消费者证明这些接口值得长期维护？ |

上次[代码审计](compiler-complexity-audit.md)提供的实测基线是：0.5 手写有效代码 18,237 行，语义检查加类型／布局占 52.7%。Core S 原型及直接复用的手写代码为 4,552 行，但不具备完整 Core S、完整命令行构建闭环或自举能力。两者不是等功能比较，不能相减得到可实现的节省量。

尤其需要纠正一个表述：0.5 Core 并未实现完整 Rust 式借用／所有权证明；它维护引用、移动等语义和供 Extend 分析的事实。不能把本次简化说成“删掉一个已经存在的完整借用检查器”。参见[正式参考的边界](../reference.md)和[审计](compiler-complexity-audit.md)。

### 项目边界也是语言边界

[SOS 的现行需求记录](../../../SOS/REQUIREMENTS.md)仍将 Rust／Zig 作为基础系统的待选实现语言，把自研语言列为后续切片；其一万行核心草案没有包含自研编译器。它也要求 GUI 与程序生命周期闭环。因此不能把“一万行系统核心”和“包含完整工具链的自举生态”当成同一个已经确认的预算。

本研究将 biomiya 视为可以进入这条教学链的候选语言，并未据此决定整个 SOS 改用 biomiya。现有 `examples/hello.vt` 和 SOS 启动示例只能验证很小的用法，不能代表文件、GUI、回收、调度或编译器自举的需求。测试夹具证明某项语言能力可用，不证明它是产品所需。

## 2. 外部语言：它们把复杂度放在哪里

下面的“适合借鉴”是针对本项目的判断，不是通用语言排名。支持裸机、生成小二进制、自举、实现很小，是四件不同的事。

| 语言／项目 | 已核实的设计取舍 | 成本与边界 | 对本项目的借鉴 |
| --- | --- | --- | --- |
| **Hare**，现代系统语言 | 无用户泛型、宏和 comptime；手动管理内存；支持 freestanding | 后端使用 QBE；裸机仍须提供运行时；不提供 Rust 同等级内存安全保证 | 最接近“保留实用数据类型、拒绝通用元编程”的参照。[设计](https://harelang.org/blog/2022-11-27-hare-is-boring/)、[FAQ](https://harelang.org/documentation/faq.html) |
| **Zig**，现代系统语言 | 显式分配器、无隐式运算符调用；类型是编译期值，comptime 支撑泛型 | 编译期执行、类型构造和运行期代码之间有复杂交互；裸机友好不意味着编译器小 | 借鉴显式分配和错误路径，不照搬 comptime。[设计](https://ziglang.org/learn/why_zig_rust_d_cpp/)、[comptime](https://ziglang.org/documentation/master/#comptime) |
| **Odin**，现代系统语言 | 普通过程配合数据结构，无方法；显式内存管理、分配器和 context；有泛型 | 动态数组、映射、类型内省等仍由语言与运行库承担；默认 context 也是调用约定的一部分 | 借鉴 arena 和数据组织；本项目更适合显式 ctx 参数。[FAQ](https://odin-lang.org/docs/faq/)、[总览](https://odin-lang.org/docs/overview/) |
| **C3**，现代系统语言 | 在 C 路线上增加模块、错误处理、契约、泛型模块、语义宏等 | 完整 C ABI、SIMD、重载和 LLVM 后端扩大实现范围 | 用作“现代 C 的舒适性会带来哪些承诺”的对照，不作为极简实现模板。[设计目标](https://c3-lang.org/getting-started/design-goals/) |
| **Rust**，现代内核开发参照 | Linux 内核以 `no_std` 使用 Rust 的 core，不能链接 std | 去除标准库不会去除语言本身的类型、借用及泛型机制 | 使用成熟 Rust 编写系统，与自制一个具有 Rust 保证的语言，是两种预算。[Linux 文档](https://docs.kernel.org/rust/general-information.html)、[区域推断实现](https://rustc-dev-guide.rust-lang.org/borrow-check/region-inference.html) |
| **Austral**，实验性系统语言 | 线性类型、能力、显式类型、无析构／GC／异常；另有类型类与泛型 | 安全性依赖受限资源使用规则与区域引用，并非仅多一个 `linear` 标记 | 若静态资源保证成为核心教学目标，优先研究这种受限设计，而非立即增加完整非词法借用。[特性](https://austral-lang.org/features)、[规范](https://austral-lang.org/spec/spec.html) |
| **Vale**，实验性安全语言 | 代际引用在访问时检查对象是否仍有效 | 成本转到对象／引用元数据、分配器和运行时检查；官网已标注归档，后继为 Valen | 借鉴受控对象表的代际句柄；不把旧站愿景当成成熟实现保证。[状态](https://vale.dev/)、[引用检查机制](https://vale.dev/memory-safe) |
| **Virgil**，研究型系统语言 | 编译器和运行时自举；同时有解释执行、类型参数、类与代数数据类型 | 全程序优化和原生目标 GC 需要编译器／运行时共同提供布局及根信息 | 借鉴“整套实现可在自身中表达”；小二进制不代表小编译器。[项目](https://github.com/titzer/virgil)、[GC 实现说明](https://github.com/titzer/virgil/blob/master/doc/impl/Gc.md) |
| **Pre-Scheme**，历史系统语言及复兴实验 | Scheme 子集编译到 C；同源可在 Scheme 中运行；目标端手动管理内存、无运行时闭包 | 宿主侧仍有宏、部分求值、类型推导／多态和 C 工具链 | 适合研究“同一核心在宿主调试、目标执行”；不是一个无需复杂编译器的捷径。[项目说明](https://prescheme.org/) |
| **C0**，教学语言 | 安全 C 子集加契约、GC、固定范围模运算 | 有意把手动回收从入门课移走，后续再转入 C；不是直接的裸机内核语言 | 说明教学语言必须围绕当前教学目标取舍；可以有受控应用层，但它的运行时要计入。[CMU 课程](https://www.cs.cmu.edu/~15122-archive/n18/resources.html) |
| **C\*／Selfie**，系统教学项目 | 极小 C 子集贯通自编译、RISC-U 模拟执行与虚拟化；官方给出自编译产物比较流程 | C\* 主要只有字长整数和指针，省去许多类型表达；其最小 OS 支持不等于完整现代内核 | 最值得参照“一个系统如何构成可执行教学闭环”。[项目及自举步骤](https://github.com/cksystemsteaching/selfie)、[文法](https://raw.githubusercontent.com/cksystemsteaching/selfie/main/grammar.md) |

### 最值得进一步阅读的四个案例

**Hare 的价值是愿意承认重复。** 官方明确把无泛型视为设计选择，并接受针对程序关键数据结构写具体实现。这个取舍适合规模受限的教学系统，但在 biomiya 自举时是否划算，必须用符号表、AST／IR 存储等真实数据结构验证。Hare 的 freestanding 文档还明确列出 memcpy、memmove、终止处理等接口；使用分配及动态切片时另需堆相关支持。它没有用“裸机”掩盖运行时成本。[无泛型的理由](https://harelang.org/documentation/faq.html)、[freestanding 合同](https://harelang.org/documentation/usage/freestanding.html)

**Selfie 的价值是闭环与严格限制配套。** 其文法省掉结构体、丰富整数类型和位运算等功能，以很窄的语言承载编译器和执行环境。对 konOSuba 而言，结构体、字节操作和位运算能直接呈现设备、页表、文件格式，不宜为了追逐更少的编译器代码而删掉。借鉴其端到端自举验收，保留本项目更需要的表达力。官方 README 的 12KLOC 是项目自述，不是本次同口径测量，也不能据此制定 konOSuba 总预算。[C\* 文法](https://raw.githubusercontent.com/cksystemsteaching/selfie/main/grammar.md)、[项目边界](https://github.com/cksystemsteaching/selfie)

**Austral 的价值是缩小“安全程序”的集合。** 线性资源必须按规定使用，显式区域引用又限制可表达的借用方式。可以少做推断，但仍需定义分支、循环、聚合和调用中的资源状态。它提示一个可选研究方向：用更严格的源程序限制换取更简单的检查，而非复制完整 Rust 的便利性。本文没有审计其实现，因此不声称一套可靠线性检查只需几百行。[规范](https://austral-lang.org/spec/spec.html)

**Pre-Scheme 的价值是区分开发环境与交付环境。** 宿主解释执行有助于观察和调试，目标端则遵守更有限的运行模型。这与 SOS 的宿主化方向相关，但 MMIO、并发、地址宽度和陷阱仍须在目标上验证。其类型推导、宏和编译期执行并不符合 biomiya 本轮的缩减方向。[语义与限制](https://prescheme.org/)、[复兴项目说明](https://prescheme.org/posts/announcing-the-pre-scheme-restoration.html)

这些案例也说明：**自举所需的是一组足够表达自身的数据结构和操作，不是面向所有用途的泛型库。** 反过来，自举成功也不能证明语言简单、安全，或已能承载 GUI／持久化系统。

## 3. 对 biomiya 的具体取舍

以下把“机制应退出主线”与“需要对照验证的进一步限制”分开。前者有本地代码成本证据；后者尚无净节省实测。

### 3.1 优先退出主线的整套机制

| 取舍 | 实际消除的责任 | 替代与代价 |
| --- | --- | --- |
| 无用户泛型、无依赖类型参数的数组长度 | 模板检查、实例缓存、实例递归／依赖、保留环境后的表达式重放 | 具体容器和具体函数；重复代码必须计入；不用代码生成器偷偷恢复泛型 |
| 无求解型推导 | 类型变量、统一、出现检查、跨兄弟表达式传播、默认修复 | 函数签名明确，局部依已知类型检查；无法局部定型时要求注解 |
| 无用户编译期程序 | 常量块环境、控制流解释、用户函数执行及相关阶段交互 | 有限整数常量、布局查询、静态数据；复杂表显式初始化或用单列计量的生成工具 |
| 无隐式移动／引用适配与资源分类组合 | Copy/resource 传播、再借用、临时生命周期及分布式语义事件 | 普通值复制、原始访问显式；泄漏／双重释放／悬垂的责任必须另行处理 |
| 无方法查找、重载、递归模式 | 接收者适配／搜索、候选消歧、模式矩阵 | 普通函数、浅层标签匹配、显式嵌套分支 |

上述方向大体与 Core S 一致。删泛型却增加通用宏，或取消 CTFE 却加入可执行的“静态构造 DSL”，很可能重新引入同类成本。库需要什么就先写什么，不先建立可容纳任意未来需求的框架。

### 3.2 类型推导：删求解器，不必制造无收益的繁琐

Core S 当前要求所有局部变量写类型，并拒绝 `if n == 0`。这有明确规则优势，但不是消除求解器的唯一方案。

可以试验一个更易用而仍局部的规则：

- `let x = known_call();`：调用签名已有确定返回类型，直接使用。
- `let x = 1;`：没有类型来源，要求注解／后缀；不做默认整数选择。
- `n == 0`：先定型左操作数 n，再按该类型检查右侧 0。
- `0 == n`：若左侧不能定型，要求 `0_u32`；不回头求解左侧。
- 函数参数、结果、结构字段仍显式；分支之间不互相补型。

这是一个有意不对称的单向规则，需衡量可教性；不能把它偷偷扩展成“总能从某处找到类型”。它不需要未知类型变量、统一或重试。应对照现有严格 Core S 测量，而不是宣布所有局部推导天然昂贵。

### 3.3 常量与布局：进一步切断反馈依赖

Core S 虽无 CTFE，仍允许常量、数组长度、对齐、布局和静态初始化形成统一依赖图。例子 `const N = sizeof(A); struct A { bytes:[N]u8 }` 要识别跨类别循环。其复杂度已经低于泛型环境重放，但仍不是普通常量折叠。

建议试验**分阶段的有限规则**：

1. 布局前整数常量只由字面量、同类常量和有限算术组成。数组长度及对齐参数只能使用这一类常量。
2. 具体类型随后计算布局，按值递归拒绝，指针不要求先得到目标布局。
3. `sizeof/alignof/offsetof` 可用于之后的常量、断言和运行时代码，但结果不得再流回数组长度／对齐。
4. 静态初始化最后处理，保留字段构造、字节串及需要的符号重定位；不执行用户代码。

因此固定页表 `[512]u64` 合法；`allocate(sizeof(Node), alignof(Node))` 合法；`static_assert(sizeof(Header) == 16)` 合法；`[sizeof(Node)]u8` 不作为首版类型允许。要存一个 Node，优先声明 Node 或在运行时分配对应存储。

这仍需要常量引用环、类型递归、整数溢出和初始化合法性检查。**消除的是常量与布局互相反推，不是所有依赖图。** 具体如何标识布局前常量应在原型里决定，本文不引入新的正式关键字。全局静态子对象取址／复杂重定位也可后置，先满足函数地址和静态根地址。

主要代价：某些通用字节存储和复杂静态表必须重写；如果编译器自举确实大量依赖它，再用用例讨论恢复哪一条规则。

### 3.4 控制流：保留清理，限制嵌套提前退出

建议保留语句式 if／while／match、显式返回、浅层穷尽检查和 Core S 的词法 defer。模块、枚举、清理对系统代码可读性有实际价值。

`defer` 不等于自动资源管理：捕获何时读取、返回值何时保存、break／continue 退出哪些作用域必须定义；panic 不展开也必须明确。仅允许 `defer f(x)` 仍有名字捕获和参数求值时机问题，不能凭语法短就认定更简单。

错误传播进一步试验：只允许 `let x:T = f(...)?;` 这一类独立语句位置，禁止 `combine(a(), f()?, b())`。程序员先把中间结果命名，编译器不再为任意子表达式中的错误出口维护部分求值状态。普通参数求值顺序和快照仍必须保留；前提不能是“后面没有副作用”。

暂不优先删固定 `Option/Result`：它们是封闭类型构造，不会恢复用户模板执行。另一方案是每个子系统定义具体结果枚举，再显式 match；但这会增加重复声明和错误处理。应在分配回滚和解析器两个样本中比较，不能把普通泛型成本全算在固定 Result 头上。

### 3.5 内核机制：缩减编译器特权，不缩减硬件合同

**建议优先试验把 `@trap_entry/@trap/@irq` 和专用尾转移移出核心语言。** 一个固定平台完全可以由汇编保存现场、调用普通 C ABI 处理函数、恢复现场并执行返回；帧布局、调用约定和中断状态写在可读的平台合同中。后续如果需要切换到其他帧／栈，必须另行实现并验证，不能把普通 C 函数返回当成抢占调度。

这会失去编译器对特殊入口签名、调用位置的专门拒绝，需用显式原型、链接检查、布局断言和目标执行验证替代。它也不会自动保证处理函数不睡眠、不重入或帧有效；现有专用属性本身也不是这些跨调用链性质的完整证明。平台代码仍计入交付成本。

其他接口区别处理：

| 接口 | 建议 | 原因及不能省略的部分 |
| --- | --- | --- |
| 普通／C 调用约定 | 固定 RV64，保留内部确定规则；C 只开标量／指针 | 不承诺任意 C 聚合、varargs、跨平台；超寄存器参数、栈对齐仍要正确 |
| MMIO、volatile | 保留有限宽度操作，或明确的汇编函数 | 单次同宽访问、设备顺序不能退化成普通内存读写 |
| 原子 | 以 Core S 的 u32／u64、SC 子集为候选 | 弱内存序可后置；不能因调用了外部汇编就认为语言侧排序已自动正确 |
| CSR、陷阱返回、设备 fence | 固定平台汇编／有限内建 | 不实现通用 inline asm 约束系统；必要时先调用普通外部汇编函数 |
| 四类指针地址空间 | 与普通指针加具名地址结构做对照 | 标记可防误用，但不能证明映射／寿命；取消后会失去部分静态区分，不宣称等价 |
| 外部符号／节名 | 收窄为项目实际使用的字符集合 | 不维护任意非 UTF-8 ELF 名字的转义、旁路恢复链；链接脚本和自研支持仍计量 |

把 MMIO／原子移到外部函数的前提是：编译器对这些调用保守处理内存副作用并保持所需顺序，平台兑现机器级协议。若未来优化器需要识别它们，少量内建往往比复杂 FFI 效果系统更简单。因此不建议为了减少“内建数量”无条件外移全部机器操作。

### 3.6 安全：三条路线必须明确选择

| 路线 | 核心代价 | 能保证什么 | 判断 |
| --- | --- | --- | --- |
| 普通值复制＋显式原始访问 | 基础类型、边界检查、访问合同；应用维护资源协议 | 不保证无悬垂、单次释放、无竞争 | 建议作为当前机制教学主线的候选，但需原型验证应用负担 |
| 受限线性资源＋词法借用 | 使用次数／状态、分支与循环一致性、聚合及调用规则 | 在所允许子集与可信边界内证明资源使用性质 | 若“静态资源安全”是核心教学内容，值得独立试点；不能当免费增量 |
| 受控对象表／GC／运行时检查 | 元数据、分配器、回收或查表检查、目标适配 | 只能在所管理的对象和访问路径内给出相应保证 | 适合应用层／执行器，不自动覆盖原始内核地址或 DMA |

对复制路线，配套库应明确几种简单生命周期：编译阶段使用 arena；固定对象使用池；跨调用持有的文件／窗口资源使用具名句柄与显式关闭。代际句柄可在槽位复用后发现部分过期引用，但还需处理代际计数回绕、并发查找／回收、句柄伪造与权限问题；不能宣称全内存安全。

普通局部建议要求初始化。为了底层存储支持而允许未初始化槽时，可将声明和操作限制在显式 unsafe 作用域；不要为了保留任意位置的 `var x:T;` 再增加一套完整流敏感证明。禁止未初始化声明与证明所有 raw 写入完成，是不同难度的承诺。

边界检查、明确算术行为、const 写入拒绝、枚举穷尽和模块访问控制仍值得保留。它们的规则可局部解释，也能减少读者面对的错误面。对于有符号溢出、移位、除法等不能为了缩行默默继承 C 的未定义行为；保持现有明确规则，再评估是否需要单独的模运算教学子集。

### 3.7 教学工具与表示：只维护实际被使用的接口

Core S 仍计划 Extend 的通用只读接口。建议首版只保留必要源码位置、类型身份和可打印 IR，先实现一个具体可用的检查／展示工具，再提炼共享接口。暂不承诺旧 Extend、外部手写 MIR、多个优化后端、跨版本插件稳定性。

删除空框架不是放弃后续分析；保留所有可能的分析事实也不等于已经提供保证。现有旧版直接 MIR 输入与源程序路径的双重支持，确实需要维护两边的合法语义；若首版只接受源码，后端可以只接受规范化 IR。

也不必强求单遍：先收集声明，再算具体布局，再逐函数检查／生成控制流，是可读的有限流程。AST、类型表、IR 可以保留；需要避免的是多层反复解释同一源语义。

## 4. 建议的候选边界

这是一组可以整体拿去验证的边界，不是另起一份已经冻结的语言规范：

- **目标**：一台固定 RV64 机器配置，一条主要编译链；所有工具和平台依赖明确列出。
- **数据**：固定宽度整数、bool、具名结构、带标签枚举、固定数组、切片、原始指针、非捕获函数指针；暂留封闭 Option／Result。
- **组织**：显式模块和可见性、具体函数和签名；无用户泛型、trait、宏、方法搜索、闭包、重载。
- **类型检查**：已知类型的单向传播；仅试验能够直接定型的局部省略，不恢复统一求解。
- **执行**：普通值复制，无隐式分配和析构；明确求值顺序、边界与算术检查。
- **控制流**：语句、浅层 match、词法 defer；错误传播限定位置；panic 终止不展开。
- **编译期**：布局前整数常量、具体布局、布局后查询与有限静态初始化分层；无用户编译期程序。
- **平台**：标量／指针 C FFI、有限机器操作、显式汇编入口；无通用汇编约束系统或语言级调度承诺。
- **安全边界**：未实现的所有权、借用、阻塞和并发分析明确不提供；不以 unsafe 语法的存在宣称“安全语言”。

不建议为了编译器最小而优先删除结构体、枚举、切片或模块，把一切变成 `usize`、手算偏移、裸状态码。那会让读者在每个系统模块重新承担类型和布局的解释工作。

Unicode 标识符也不是此次核心矛盾：2,095 行生成表已单列，删掉它不会等额减少手写语义复杂度。是否改成 ASCII 应由读者和文档需求决定，不能用它伪造主要缩减成果。

## 5. 如何防止“编译器变小，整个系统变大”

按同一组程序比较：

**交付代码 = 编译器＋运行支持＋平台代码＋必要库＋生成工具＋示例。**

测试和文档另列，第三方基础设施单列。还应记录重复的容器实现、跨模块资源协议、读懂一条路径需要经过的文件／规则，以及运行时开销。LOC 只是其中一项。

### 最小验证语料

| 样本 | 要检验的语言承诺 | 通过条件 |
| --- | --- | --- |
| 位图页分配器与页表操作 | 整数／位操作、对齐、布局、原始访问 | 分配失败、重复释放检测策略、页表编码与真实目标执行明确 |
| 带中断保存的锁与 UART | 原子、MMIO、汇编边界、defer | 访问宽度／顺序、中断恢复和清理路径正确；单 hart＋IRQ 与多 hart 分开声明 |
| 文件句柄表和失败回滚 | 普通复制、显式责任、Result／? | 每个失败点和关闭路径的责任可跟踪；无隐藏通用容器 |
| 编译器符号表、AST arena、类型表 | 无泛型、有限局部推导、内存策略 | 记录重复实现、转换和总支持代码；诊断不是只输出成功／失败 |
| 加载小程序、处理事件、更新并关闭窗口 | 函数指针、模块、应用资源寿命 | 应用退出能撤销登记并释放资源；检验语言能否支撑 SOS 的真实目标 |

这些是待做的验证，不是本次已完成的测试。其顺序应先覆盖语言最可能失效的地方，而不是先补齐所有语法夹具。

### 对照实验与停止条件

1. **先接通现有 Core S 原型。** 它还缺完整驱动／平台闭环；接通后的实际账本是后续比较基础。不把现有 4,552 行当最终规模。
2. **固定上述语料和行为。** 给每个原需求标记“保留／有意拒绝且已迁移／尚未支持”。尚未支持不能计作完成简化。
3. **分别比较三个变量。** 严格显式类型与有限局部省略；统一常量／布局图与分阶段规则；特殊陷阱语义与汇编加普通 ABI。避免同时重写全部设计后无法归因。
4. **核算删除与迁移。** 真正移除旧算法、接口和依赖；记录新增库／平台代码、重复及需要人工维护的合同。不长期靠旧实现兜底维持表面通过。
5. **验证自编译，再验证系统内自举。** 能编译一个 biomiya 编译器是第一关；在目标系统内读取源文件、编译、得到并运行下一代工具是另一关。确定性构建时比较后续代产物，并保留行为测试；相同产物不是完整正确性证明。

若无泛型使少数关键结构各有清楚具体实现，取舍成立；若出现大量重复容器、宏生成器和类型擦除适配，应重新讨论受限复用机制。若删平台语义仅换来一套更大、更难核查的注解／代码生成系统，该项不成立。若为了凑目标行数而省去关键行为或诊断，规模结果不予采用。

不再先承诺“完整编译器应当是 4–6 千行”。先用同范围闭环得到第一份可信规模，再制定上限；新的功能只有明确服务于教学场景、说明新增机制及跨层代价后才进入主线。小生态成立的条件是系统主动选择有限的数据结构、平台和生命周期，并让语言恰好覆盖它们。
