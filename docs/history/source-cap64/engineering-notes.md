# C64 工程记录

2026-10-15；作者记录，候选尚待独立验收。原始日志在 ignored build 中，最终身份见候选。

## 容量常量未约束实现

- 症状：`model::SOURCE_CAP=32` 存在，但 input 的两个判界、三个表/清零范围仍直接写32/33，单改常量不能扩容。
- 证据：基线 `d2c6e98` 的 compiler/model.vt、input.vt、types.vt；此次源码差异。
- 已确认原因：声明容量与存储长度、运行时判界分离维护，没有引用关系；不是此次测试中新发现的运行崩溃。
- 处理：判界、清零和三个表长度统一使用 SOURCE_CAP，表长度为 `model::SOURCE_CAP as usize + 1_usize`，保留索引0和固定静态布局。64文件实际访问和65文件拒绝、两轮输入状态测试覆盖对应关系。
- 启示：固定容量有利于理解成本，但公开常量如果只是说明会制造假象。以后新增容量应同时列出拥有者、存储、重置、判界和边界回归。此次不扩展数组长度语法或其他容量。

## 模块数同时约束递归深度

- 症状：types::module_constants 沿模块import递归，因此文件数扩至64也会增加可达调用链深度。
- 证据：compiler/types.vt 的 module_constants/collect；新 modules-64-chain/cycle 回归。
- 已确认：递归由实际模块数量及访问状态约束；prepare_depth32是另一个声明/类型准备边界，不能跟随文件数一起翻倍。
- 处理：保留1MiB guest栈和prepare_depth32，已在既定1MiB栈下验证64模块长链返回63、末端环正常E_NAME拒绝。对应记录为build/source-cap64-check_q_interfaces-r2/verification.json。
- 启示：容量不是单纯数组长度；扩容须跟踪算法深度和调用栈。是否改成显式遍历栈属于后续架构选择，本节点没有据此扩大重构。

## 旧P3记录拒绝复用

- 症状：首次P4在启动编译前拒绝：`current input differs from accepted evidence: tools/check_next.py`。
- 证据：build/source-cap64-p4-r1.log 和对应 verification.json。
- 已确认原因：旧 layout-p3-r1 记录的工具字节与当前工具不同。证据检查正常生效，不是编译器BUG，也不是需要跳过的限制。
- 处理：保持旧记录和冻结bootstrap不变，使用相同冻结seed重新跑P3，生成 build/source-cap64-p3-r1；126语言案例与11 retained target checks通过，再开始P4-r2。
- 启示：重用证明不仅取决于产物哈希，还取决于验证输入身份。应清楚区分“无法沿用旧证据”和“实现运行失败”。

## 固定表长度可以由容量常量派生

- 症状：首轮实现把表长度改成literal65并注释对应SOURCE_CAP，仍有未来漂移可能。
- 证据：root提出结构建议后，使用实际P3/E0编译跨模块常量数组长度表达式并运行，第64项读写返回42；输入和compile.log保存在build/source-cap64-array-probe。
- 已确认：完整引导所用P3支持该表达式，literal不是冻结语言限制；此前只是沿用旧写法，不能据此宣称编译器不支持。
- 处理：三个表都派生SOURCE_CAP，主动停止未完成的P4-r2及并行回归，保留superseded.json、已生成产物和日志，按新源码执行P4-r3与回归。P4-r2不是完整通过证据；新派生写法产物与literal65写法ELF相同，但最终源码身份以r3记录为准。
- 启示：优先用现有语言能力表达结构关系；确有旧stage限制时再用实证说明妥协，不把未经验证的假设变成永久样板。
